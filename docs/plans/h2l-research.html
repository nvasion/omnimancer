1. What H2L is

H2L is a two-tier agent flow. A high model acts as the principal engineer: it reads the repository, produces a design, and breaks the work into a backlog of stories. Each story is written for a junior who cannot see the repo: absolute paths, exact strings to replace, exact commands to run, and explicit acceptance criteria. A pool of low models executes the stories in isolation, one story per worker, using only the instructions they were handed. The high model then judges each result against the story's acceptance criteria and either accepts it, sends it back with feedback, or escalates.

High tier · plans
Principal

Reads the repo with the full tool set. Writes a design and a backlog of explicit stories. Submits the plan through a tool schema.

Low tier · executes
Worker pool

One story per worker, own provider instance, own history. Edit, Write, Bash only. No exploration. Returns a diff and verify output.

High tier · scores
Judge

Deterministic checks first, then the high model grades the diff against the acceptance criteria. Below threshold goes back with feedback.

Three properties separate this from "just use subagents":

  1. Workers are deliberately context-poor. They do not explore the repo. The planner does all the reading, and run quality is bounded by how explicit the stories are.
  2. Workers are a pool, not a single model. The user supplies a list of low models; the scheduler assigns stories across them and can run them in parallel.
  3. There is a judge loop. The high model scores every result before it counts as done. Failed stories are retried with the judge's feedback attached.

Both the TUI (omn) and headless (omn -p) must support it. Models come from config in the TUI and from flags in headless.

Judge bias. The literature is consistent that LLM judges favor verbose, confident output and output resembling their own style. The mitigation baked into this design: the judge sees the actual diff and test output, never the worker's narration, and cheap deterministic checks run before the judge sees anything.

4. Codebase findings

4.1 The subagent runner is the right seed, with seven known gaps

cli/subagent.py (176 lines) runs a SubAgentDefinition to completion: isolated ChatContext, tool allowlist, optional model override, capped iterations, and fleet lifecycle events with a unique run id and parent id. Tests live in tests/cli/test_subagent.py. Gaps, in order of how much they matter to H2L:

  1. Shared provider mutation. The runner sets provider.model on the parent's live provider and restores it in finally. Two concurrent runs with different models would clobber each other. This blocks parallelism outright.
  2. No history accumulation. context.messages stays empty for the whole run; continuity is a rewritten "Tool results" message. A worker that edits, tests, and edits again needs real history.
  3. Not model-invocable and not headless-reachable. The only entry is the /subagents run slash command. No Task tool, no marker.
  4. Results never re-enter a conversation. Printed as a Rich panel. SubAgentResult holds only the last text and tool names, no diff and no arguments. A judge needs more.
  5. Tool allowlist is advisory. It filters definitions sent to the model, but execution never re-checks.
  6. ToolResult.cancelled is ignored inside the loop.
  7. The definition prompt is folded into the first user message, not sent as a system message.

Recommendation: do not extend SubAgentRunner in place. Build a new WorkerRunner for H2L that fixes all seven, then consider re-basing the subagent runner on it later.

4.2 Provider and model binding: the safe pattern already exists

The model is a plain attribute on every provider instance, set at construction. CoreEngine.providers holds one live instance per config entry, and current_provider points into that dict. Two ways to run a different model exist today:

  • Mutate the shared instance. switch_model and the subagent runner do this. Fine for one conversation, unsafe under concurrency.
  • Build a second instance. The prompt enhancer copies the provider config with model_copy(update={"model": ...}), calls ProviderFactory.create_provider, and talks to the new instance with its own ChatContext. The initializer's cache key includes the model, so one provider with two models yields two distinct instances.

H2L must use the second pattern for every worker and for the planner. This is the single most important implementation constraint.

Alias entries matter here. A config entry named gateway with provider_type: "openai-compatible" is a first-class provider name, which is how a local vLLM or Ollama endpoint becomes a low model. H2L model tokens should therefore be <provider-entry>:<model>.

4.3 Only tool-capable providers can be workers

Workers execute through native tool calls. Providers whose supports_tools() is false cannot be workers today: ollama, cohere, perplexity, and claude-code. The Ollama gap is the painful one, because local small models are the obvious low tier.

Workaround that already works. Point an openai-compatible alias at Ollama's OpenAI-compatible endpoint, which accepts tools. The PRD should either document this or add native tool support to the Ollama provider as a prerequisite story.

4.4 Two agent loops, no shared turn function

The interactive loop in cli/interface.py and the headless loop in cli/headless.py are separate implementations of the same idea. They differ in iteration cap, checkpointing, history elision, streaming, and approval wiring. The shared pieces are ToolHandler, RepeatedCallTracker, build_agent_prompt, TokenAccumulator, the fleet events, and the approval gate.

Consequence: the H2L worker loop must not be written a third time inside each surface. It should be one module that both the /h2l command and the headless runner call. It is small and bounded, so it is a good first shared loop.

Headless also has no marker fallback. A non-tool provider under omn -p emits markers as dead text. H2L should reject non-tool providers for both tiers at validation time.

4.5 Config surface

There is no global default model. The model lives on each provider entry, and default_provider picks the active one. Three role-like precedents exist for an h2l block: EnhancementConfig (opt-in by presence), SubAgentDefinition.model, and FallbackConfig.fallback_order.

Precedence gotcha. Order is env > CLI flags > stored config, and apply_env_overrides runs inside provider initialization, after session overrides, assigning unconditionally. H2L flags must resolve their model tokens after provider initialization or an OMNIMANCER_<PROVIDER>_MODEL variable will silently rewrite a tier.

The CLI is a single click command, deliberately not a group because external orchestrators parse omn -p --help. New flags must be plain options on it. Session flags never persist, and a regression test keeps the config file byte-identical.

4.6 The approval and security gate

Every operation from either path funnels through execute_with_approval: preview, permission rules, the blocking tool_use_request hook, the approval callback, execution, then the observe-only post_tool hook. Hard-restricted paths have no bypass at all. Three facts shape H2L:

  1. Approval prompts block stdin via asyncio.to_thread(input). Parallel workers hitting write prompts would interleave on the terminal. H2L needs a lock around the callback so prompts arrive one at a time, each naming the worker and story.
  2. Headless is deny-by-default. Without --dangerously-skip-permissions no worker can write or run anything. Factory already passes the flag.
  3. Approval is per operation, not per story. A plan-level gate in the TUI is a new concept that fits the existing philosophy and is where the user edits or drops stories.

4.7 Observability is nearly free

events/emitter.py keeps the agent id and parent id in ContextVars, so agent_context propagates correctly across asyncio.gather. Every tool event already carries both ids. The Fleet TUI renders subagent rows as indented children, TurnActivityLog groups by agent id, and StreamingDisplay exposes an activity_provider callback as the one sanctioned injection point. A per-worker REPL view is a display change, not new instrumentation.

4.8 Code to avoid

  • core/agent/workflow_orchestrator.py is instantiated on every engine start and never driven. Its steps wrap Python callables, not model instructions.
  • AgentModeManager has a concurrency queue the live loop does not use, and its execute method is a stub.
  • core/agent/config.py is a parallel config system with zero instantiations.

5. Proposed architecture

A new package, omnimancer/h2l/, with five modules. Both surfaces call into it.

h2l/models.py

H2LModelRef, H2LConfig, Story, Plan, WorkerReport, Verdict. Pydantic, mirrored as tool schemas.

h2l/planner.py

High model, fresh instance, full tool set. Returns the plan through a submit_plan tool call, never free JSON.

h2l/worker.py

WorkerRunner.run(story, model_ref). Own instance, real history, allowlist enforced at execution, Read scoped to story.files, captures diff and verify output.

h2l/judge.py

Deterministic checks short-circuit. Then the high model grades diff plus verify output against acceptance criteria via submit_verdict.

h2l/orchestrator.py

DAG from depends_on plus implicit shared-file edges. Semaphore, round-robin pool, approval lock, events, plan checkpoint.

5.1 Data model

class H2LModelRef(BaseModel):
    provider: str            # config entry name, e.g. "claude", "gateway"
    model: str

class H2LConfig(BaseModel):
    enabled: bool = True
    high: H2LModelRef
    low: List[H2LModelRef]   # the worker pool, ordered
    max_parallel: int = 2
    max_retries: int = 2     # judge send-backs per story before escalation
    pass_threshold: int = 80 # judge score 0..100
    worker_tools: List[str] = ["Edit", "Write", "Bash"]
    allow_worker_read: bool = True   # Read limited to story.files

class Story(BaseModel):
    id: str
    title: str
    instructions: str        # imperative, explicit, no exploration required
    files: List[str]         # absolute paths the worker may touch
    acceptance: List[str]    # criteria the judge scores against
    verify: Optional[str]    # shell command; exit 0 required
    depends_on: List[str] = []

class Plan(BaseModel):
    goal: str
    design: str
    stories: List[Story]

class WorkerReport(BaseModel):
    story_id: str
    worker: H2LModelRef
    success: bool
    narrative: str           # worker's final text (shown, not graded)
    tool_log: List[dict]
    diff: str                # git diff limited to story.files
    verify_output: Optional[str]
    verify_exit: Optional[int]
    files_outside_scope: List[str]

class Verdict(BaseModel):
    story_id: str
    score: int
    passed: bool
    failures: List[str]
    feedback: str            # sent verbatim to the worker on retry

5.2 Planner

Runs the high model on a fresh provider instance with the full coding tool set so it can read the repo. Its system prompt says, in effect: you are writing for a worker that cannot see the repository and will not explore; every story must contain absolute paths, exact text for Edit or full content for Write, exact commands, and testable acceptance criteria; stories touching the same file must declare a dependency. The plan is returned through a submit_plan tool call whose schema is the Plan model. Every tool-capable provider enforces tool schemas, which makes this reliable across vendors.

5.3 Worker

  • Fresh provider instance per worker via create_provider on a model_copy.
  • Real ChatContext history that accumulates every turn.
  • System prompt written for someone who follows steps literally: do exactly what the story says, do not explore, if an Edit old string does not match then stop and report it.
  • Tool allowlist enforced at execution time. Read only for paths in story.files.
  • Captures tool arguments and results, a git diff scoped to story.files, the verify command output, and any file touched outside scope.
  • Honors ToolResult.cancelled. Runs inside agent_context(f"h2l-{story.id}-{hex}", parent=run_id).

5.4 Judge

Deterministic checks first, and they are free: non-zero verify exit, any out-of-scope file modified, or an empty diff on a story that requires edits each fail immediately. Only then does the high model see the story, the acceptance criteria, the diff, and the verify output. It does not see the worker's narrative. A score below pass_threshold sends the story back with feedback prepended, up to max_retries, after which the orchestrator escalates: the high model does the story itself, or the run marks it blocked. Configurable.

5.5 Orchestrator

  • DAG from depends_on plus implicit edges between stories that share a file, so concurrent edits to one file never happen.
  • Ready stories run under asyncio.gather with a semaphore of max_parallel.
  • Round-robin assignment from the pool; a retried story goes to the next model, a cheap form of diversity.
  • Approval callback wrapped in an asyncio.Lock, each prompt stamped with worker and story.
  • Emits h2l_plan, h2l_story_start, h2l_story_report, h2l_story_verdict, h2l_done on the fleet bus and as stream-json lines.
  • Checkpoints the plan plus per-story state so omn --resume restarts at the first unfinished story.

5.6 TUI surface

  • /h2l <goal> plans, shows the stories in a table, asks for approval (edit, drop, accept), then runs the pool with a per-worker activity panel.
  • /h2l plan <goal> stops after the plan. /h2l run executes the last plan. /h2l status and /h2l config for inspection.
  • The h2l block in ~/.omnimancer/config.json follows the enhancement precedent and is opt-in by presence.

5.7 Headless surface

omn -p "Add rate limiting to the webhook handler" \
  --h2l \
  --high claude:claude-opus-5 \
  --low gateway:qwen3-8b --low ollama-oai:qwen2.5-coder-14b \
  --h2l-parallel 2 \
  --output-format stream-json \
  --dangerously-skip-permissions

Flags override the config block; missing flags fall back to config. No high model from either source exits 1 with a clear error. Exit codes reuse the existing contract: 0 done, 1 error, 3 partial with blocked stories, 4 rate-limited and resumable. The final JSON result gains a stories array with per-story verdicts and usage split by tier.

6. Design decisions and rationale

  1. Never mutate a shared provider. Every participant gets its own instance from the factory. This is what makes parallelism safe and matches the enhancer.
  2. Structured outputs through tool schemas. submit_plan and submit_verdict are tools. Works on every tool-capable provider without JSON repair.
  3. Workers get the smallest tool set that can do the job. Edit, Write, Bash by default, Read scoped to the story's files. If a worker needs to search, the story was under-specified and that is the planner's bug.
  4. Deterministic checks before the judge, and the judge grades the diff. The direct answer to judge bias, and it keeps judge tokens low.
  5. File-conflict-aware scheduling now, worktrees later. Implicit edges between stories sharing a file remove the write race cheaply. Per-worker worktrees are the v2 answer.
  6. One worker loop, two surfaces. Build it once in omnimancer/h2l/ and call it from both command_dispatch.py and headless.py.
  7. Reject non-tool providers at validation time. Both tiers require supports_tools(). Fail early with a message naming the alias workaround.
  8. Plan approval is a first-class gate in the TUI. Headless skips it under --dangerously-skip-permissions; otherwise the run stops after the plan and prints it, which doubles as a dry-run mode.

7. Risks and open questions for the PRD

  • Story quality is the whole game. Vague stories mean blind workers fail and the judge loop burns tokens. The planner prompt needs the same care as the PromptFoundry meta-prompts, plus a self-check pass for missing exact strings before submitting.
  • Stale Edit old strings. Story N+1 may reference text that story N changed. The shared-file DAG edge orders them, but both were written against the original file. Scoped Read and the judge loop catch the rest. Worth measuring.
  • Escalation policy. After max_retries, does the high model do the story itself or does the run stop? Recommend configurable, defaulting to escalate in headless and ask in the TUI.
  • Cost accounting. TokenAccumulator totals per session. H2L should report per tier and per story, since the point of the feature is moving spend from the high tier to the low tier.
  • Ollama native tools. Document the alias workaround or give the provider tool support. The second is a small, well-bounded prerequisite.
  • Checkpoint schema. HeadlessCheckpoint is versioned at 1. Plan state either bumps it or lives in a sibling file keyed by session id. Sibling is less invasive.
  • Approval fatigue. Six workers each writing three files is eighteen prompts. The plan gate plus existing /accept modes and permission rules should be enough, but the PRD should state the default.

8. Suggested phasing

  1. Phase 1 · serial MVPModels, planner, worker, judge, orchestrator with max_parallel=1. /h2l in the TUI; --h2l, --high, --low in headless. Plan approval gate. Deterministic checks and the LLM judge. Stream-json events. Proves the loop end to end without touching concurrency.
  2. Phase 2 · parallel poolPer-worker instances already exist from phase 1, so this adds the semaphore, the shared-file DAG, the approval lock, round-robin assignment, and the per-worker activity panel.
  3. Phase 3 · resiliencePlan-level checkpoint and --resume at story granularity, per-tier cost reporting, escalation policy, optional worktrees.

9. Test plan hooks

Per the TDD rule in CLAUDE.md, each module lands with tests first.

  • tests/h2l/test_models.py: validation, model token parsing, DAG construction including implicit shared-file edges, cycle rejection.
  • tests/h2l/test_planner.py: mocked provider returning a submit_plan call; planner never touches chat_manager; shared-file stories get dependencies.
  • tests/h2l/test_worker.py: history accumulates; allowlist enforced at execution; out-of-scope Read refused; cancelled aborts; diff and verify captured; the parent provider's model is never mutated.
  • tests/h2l/test_judge.py: deterministic fails short-circuit the model call; the judge prompt excludes the narrative; threshold and retry feedback.
  • tests/h2l/test_orchestrator.py: two providers with different models run concurrently without clobbering; approval lock serializes prompts; round-robin and retry reassignment; events carry the right parent id.
  • tests/cli/test_h2l_command.py and additions to tests/cli/test_headless.py: flag parsing, config fallback, env-override ordering, exit codes, stream-json schema.
  • Provider validation: a non-tool provider in either tier fails with the alias hint.
